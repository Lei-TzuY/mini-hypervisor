# Safety assumptions

## Trust model

The Linux KVM kernel interface and explicitly supplied host process configuration are trusted. Guest-controlled addresses, lengths, CPU state, port-I/O metadata, KVM system-event type/count/data metadata, future MMIO requests, and future device requests are untrusted at userspace policy boundaries. Caller-selected guest MSR authorization inputs are validated as configuration before they can become policy state, caller-selected guest MSR value-state inputs are validated against that policy before they can become a typed value set, and full-policy MSR snapshots are created only through crate-controlled coverage/order validation. Kernel-returned variable-length metadata such as supported-CPUID, vCPU CPUID read-back, general MSR-index counts, MSR-feature-index counts, system `KVM_GET_MSRS` completion/index metadata, caller-directed vCPU `KVM_GET_MSRS` completion/index metadata, vCPU `KVM_SET_MSRS` processed-entry counts, capability-enabled internal-error `ndata`, and system-event `ndata` are validated before they are used for Rust slicing, copied into typed state, or interpreted as complete state mutation. KVM fail-entry hardware-reason and CPU fields are copied as opaque architecture-specific diagnostics and are not interpreted as retry, placement, or recovery policy. The always-available `KVM_EXIT_INTERNAL_ERROR` `suberror` field is likewise copied as opaque diagnostic state and is not interpreted as retry, recovery, or lifecycle policy. Separately, the backend records the raw `KVM_CHECK_EXTENSION` observation for optional `KVM_CAP_INTERNAL_ERROR_DATA`; a zero value is valid for the current host contract and keeps the vCPU decoder on the base `suberror`-only view, while a positive value is propagated through `Vm` into created vCPUs and authorizes only the fixed full payload view. On that capability-enabled path, `ndata` must be `<= 16` before any slice is formed and only the declared `data[16]` words are copied into owned diagnostic state. Available-but-empty data remains distinct from unavailable optional data. None of these diagnostics authorizes recovery or lifecycle action.

The current HLT, debug-port, and CPUID fixtures are repository-owned test inputs rather than arbitrary external guest content. `FlatGuestImage` nevertheless applies range and entry validation so later callers do not acquire an unchecked loading path by accident.

## Unsafe boundary in the current milestone

`src/kvm/sys.rs` contains raw `ioctl` calls. The call sites use constants and structures matching the stable x86-64 Linux KVM UAPI and convert `-1` into `std::io::Error` immediately.

Successful `KVM_CREATE_VM` and `KVM_CREATE_VCPU` results are file descriptors owned by the caller; they are immediately wrapped in `OwnedFd`.

### CPUID contract

`KVM_GET_SUPPORTED_CPUID`, `KVM_SET_CPUID2`, and `KVM_GET_CPUID2` use the variable-length `struct kvm_cpuid2` ABI. The implementation does not allocate an unaligned byte buffer and cast it. Instead, `KvmCpuid2<N>` is one `repr(C)` object containing the 8-byte header followed immediately by an aligned fixed array of `KvmCpuidEntry2` values. Pure tests lock the 40-byte entry size, header size, entries offset, and all three ioctl request values.

Both the system discovery query and vCPU read-back use a fixed capacity of 256 entries, matching the current x86 KVM maximum used by this project. Each successful kernel-returned `nent` is treated as untrusted metadata: it must be in `1..=256` before a slice is formed. A zero or out-of-capacity count is rejected as an invalid host/KVM response. Capacity failure from the ioctl itself remains a named `KVM_GET_CPUID2` vCPU-operation error rather than being retried with an unbounded allocation.

After count validation, raw KVM entries are converted into owned `CpuidEntry` values that contain only function, index, flags, and architectural register values. Reserved KVM padding is not retained in typed host or read-back state. Converting a final guest policy back into a KVM buffer always recreates the reserved padding as zero. Raw variable-length buffers never cross above the KVM module boundary.

Host capability discovery and guest policy construction are separate trust boundaries. `HostCpuid` preserves the validated KVM-supported entry values and is never mutated by policy construction. `GuestCpuPolicy::from_host` clones that snapshot and performs only the current conservative feature reduction. Pure tests require host immutability, exact preservation of unrelated fields/registers, and consistent treatment of multiple indexed entries for the same function.

The current VMM intentionally has no in-kernel LAPIC/IRQ-chip model. Linux KVM documents x2APIC, TSC-deadline exposure, and `KVM_FEATURE_PV_UNHALT` as depending on that interrupt model, so those bits are removed only in `GuestCpuPolicy`. This is a conservative feature reduction; no unsupported feature is synthesized.

`GuestCpuPolicy::compare` is pure Rust over two already-owned configured policies and performs no KVM operation. The project-level identity is the stored `(function, index)` pair exposed by `CpuidPolicyKey`; list position is not identity. A function or index change is therefore represented directionally as missing+extra, while entries with the same key are compared across exactly `flags`, `eax`, `ebx`, `ecx`, and `edx`. The comparison deliberately analyzes stored policy records rather than attempting to emulate raw CPUID lookup/index-significance rules.

Same-key differences become `CpuidPolicyEntryMismatch` values that retain both complete entries plus an explicit canonical field list in `Flags`, `Eax`, `Ebx`, `Ecx`, `Edx` order. Missing entries and mismatches preserve reference-policy order; extras preserve observed-policy order. Reordered policies with the same keyed contract therefore remain an exact match. Focused regressions lock function/index identity, identical/reordered behavior, directional missing/extra findings, single- and multi-field mismatch classification, finding order, and empty inputs.

Every `GuestCpuPolicyComparison` clones and owns both complete `GuestCpuPolicy` inputs. The result has no borrow into `KvmBackend`, `Vm`, `Vcpu`, KVM shared memory, or raw UAPI buffers. Retaining the complete inputs is diagnostic provenance only; it grants no additional execution authority and does not alter the policies that are applied or verified elsewhere.

An exact `GuestCpuPolicyComparison` result is not a migration-safety decision. It proves only equality of the configured project-level `(function,index) → flags/EAX/EBX/ECX/EDX` mapping under this comparison contract. MSR capability/value analysis, kernel behavior, device state, memory layout, time state, and other migration requirements remain outside this result.

Every `Vm::create_vcpu` call serializes the already-derived guest policy into a fresh bounded KVM buffer and applies it with `KVM_SET_CPUID2`. Before the `Vcpu` object is returned, the same descriptor is queried with bounded `KVM_GET_CPUID2`. The returned count is independently validated, entries are decoded into owned typed values, and the complete ordered list must exactly equal the submitted `GuestCpuPolicy` across function, index, flags, EAX, EBX, ECX, and EDX. A SET failure, GET failure, malformed count, count mismatch, or field mismatch closes the newly created descriptor through `OwnedFd` drop and returns a named vCPU-operation error. Higher layers therefore cannot reach this project's `KVM_RUN` path through a vCPU whose configured CPUID contract was not verified after submission.

The deterministic CPUID proof executes only two fixed leaves. Its reviewed 28-byte real-mode program stores CPUID(1).ECX at guest physical `0x2000` and CPUID(0x40000001).EAX at `0x2004`, then halts. The host does not inspect either result until the terminal HLT report has been produced. The entire eight-byte result range is read through `GuestMemory::read`, so guest-written addresses still pass the normal checked guest-memory boundary before they become host observations. Pure tests separately lock the byte sequence, little-endian decoding, and the predicate used to identify the three masked LAPIC-dependent bits.

### MSR index capability discovery

`KVM_GET_MSR_INDEX_LIST` and `KVM_GET_MSR_FEATURE_INDEX_LIST` use the same variable-length `struct kvm_msr_list` ABI: a 4-byte `nmsrs` field followed by a trailing array of `u32` indices. `KvmMsrList<N>` models this as one aligned `repr(C)` object instead of casting an arbitrary byte buffer. Pure tests lock the zero-entry and one-entry sizes, the trailing-array offset, and both exact ioctl request values.

The feature-index ioctl is not treated as a basic capability. `KvmBackend` requires `KVM_CAP_GET_MSR_FEATURES` before issuing it. This keeps unsupported kernels from reaching a feature-discovery ioctl merely because the wire structure matches the general MSR list.

Both discovery paths use two bounded queries. The first query supplies `KvmMsrList<0>`. Linux KVM writes the required count back into `nmsrs` before returning `E2BIG` when the supplied capacity is too small, so `E2BIG` is accepted as expected only at each zero-capacity probe boundary; any other probe error remains a host-I/O failure. The 1024-entry limit used for the second query is an explicit project defensive bound, not an assertion that Linux permanently caps this ABI at 1024 entries.

The two kernel contracts deliberately have different count rules. The general `KVM_GET_MSR_INDEX_LIST` count must be in `1..=1024`; zero remains malformed for the already-required general snapshot. The `KVM_GET_MSR_FEATURE_INDEX_LIST` count is validated in `0..=1024`, because a supported host may legitimately expose an empty feature-MSR set. Pure tests lock this distinction so a valid empty feature list cannot be rejected by accidentally reusing the stricter general-list predicate.

Only after each probe count passes its own validation does the backend issue the corresponding second query with a fixed `KvmMsrList<1024>`. The second returned `nmsrs` is independently validated with the same contract-specific rule before indexing the trailing array. A second-query failure or count beyond the project bound is rejected rather than triggering unbounded allocation or unchecked slicing.

Validated raw indices are copied into owned typed state. `HostMsrIndexList` and `HostMsrFeatureIndexList` both reuse `MsrIndex`, but they remain distinct types because the general MSR access set and the system feature-probing set have different semantics. Duplicate kernel indices in either list are normalized by retaining the first occurrence while preserving the kernel-reported order of retained indices; pure tests lock both behavior and the valid empty feature-list case. Raw variable-length buffers and their pointers never leave the KVM module.

### MSR feature-value capability discovery

System-level `KVM_GET_MSRS` is used only after `KVM_CAP_GET_MSR_FEATURES` has already been required and only with indices from the validated `HostMsrFeatureIndexList`. This does not use a vCPU descriptor and therefore does not read guest MSR state.

`KvmMsrs<N>` models the variable-length `struct kvm_msrs` ABI as an aligned `repr(C)` object with an 8-byte `nmsrs`/padding header followed immediately by a fixed array of 16-byte `KvmMsrEntry` values. Each entry contains the exact `u32 index`, reserved `u32`, and `u64 data` fields. Construction zeroes header padding plus every entry's index, reserved field, and data. Pure tests lock the header size, entry size, trailing-array offset, exact `KVM_GET_MSRS` and `KVM_SET_MSRS` request values, and zero initialization.

Before either raw MSR value ioctl is issued, its wrapper converts `nmsrs` to `usize` and requires it to be no greater than the actual const-generic backing capacity. This check happens before the unsafe call; focused regressions supply an invalid descriptor and an over-capacity header and still receive `InvalidInput`, proving both GET and SET wrappers reject the count before the kernel could observe the bad file descriptor. The host feature-value path uses the existing fixed 1024-entry project buffer and requests exactly the normalized feature-index count.

KVM returns the number of entries successfully processed. Kernel MSR iteration stops at the first failing entry, so a short positive return is a partial result rather than a complete snapshot. The backend accepts typed feature values only when the return count exactly equals the requested count. Partial completion is rejected and reports the first unread requested index; a count greater than requested is also rejected. No successful prefix is exposed as `HostMsrFeatureValues` after a partial result.

The request entry indices are userspace-provided and are expected to remain unchanged. After complete-count validation, the backend independently checks every returned entry index against the requested typed `MsrIndex` in the same order. An index mismatch rejects the whole response before any value is published. Only a complete, order-stable response is copied into owned `MsrFeatureValue` entries. An empty feature-index list is a valid empty value snapshot and skips the ioctl entirely.

Each `MsrFeatureValue` receives `MsrFeatureStability` inside its crate-private constructor, so external callers cannot manufacture contradictory stability metadata. Linux KVM states that all feature MSRs are immutable once the vCPU model is defined except the microcode revision feature, which tracks the currently loaded microcode patch. The x86 architectural constant is locked as `MSR_IA32_UCODE_REV = 0x8b`; that index is always classified `HostMutable`, while other feature values in the current KVM contract are `ModelImmutable`.

The stability labels are intentionally narrower than migration semantics. `ModelImmutable` means only that KVM treats the feature value as immutable after the vCPU model is defined; it does not promise equality across hosts, CPU revisions, kernel versions, or VMM configurations. `HostMutable` makes the microcode revision exception explicit. `HostMsrFeatureValues::model_immutable_values` and `host_mutable_values` are read-only order-preserving partitions over the same owned snapshot. Focused regressions require those partitions to be mutually exclusive, preserve source order, and remain empty for an empty snapshot.

`HostMsrFeatureValues::model_candidate` is the only public route to `HostMsrModelCandidate`. Candidate fields are private and its constructor remains internal to the MSR module. Materialization clones the complete stability-annotated source observation into `source_observation` and separately copies only `ModelImmutable` entries into the candidate value set, preserving their source order and data. This creates an explicit provenance chain while structurally preventing `HostMutable` entries, including `MSR_IA32_UCODE_REV`, from being supplied directly as candidate values. Pure regressions cover mixed, all-mutable, and empty source observations and require complete provenance to remain available even when the candidate subset is empty.

`HostMsrModelCandidate::compare` never reads either source observation to determine compatibility. It compares only the already-filtered immutable candidate value sets, keyed by MSR index. The result separately owns reference-missing entries, observed-extra entries, and same-index value mismatches. Missing entries and mismatches are emitted in reference order; extras are emitted in observed order. Reordered immutable entries with identical index/value pairs therefore compare as an exact model match rather than producing an order-only difference.

`HostMsrModelComparison` clones and owns both complete candidates, so both complete source observations remain available for diagnostics after comparison without introducing borrows into backend state. This retained provenance does not influence the verdict. In particular, different `HostMutable` source values such as `MSR_IA32_UCODE_REV` are still visible through the two retained source observations but cannot appear in missing/extra/mismatch findings or turn an immutable exact match into a mismatch.

The candidate derivation and comparison are pure Rust over already-validated owned host state; neither issues a KVM call nor grants new authority. An exact `HostMsrModelComparison` result is not a migration-safety decision: CPUID policy, kernel behavior, device state, memory layout, guest MSR state, and other migration requirements remain outside this contract. The host feature-model path itself does not call vCPU `KVM_GET_MSRS` or `KVM_SET_MSRS`; vCPU architectural-state readback and writes are separate caller-directed boundaries below.

### Guest MSR access policy

`GuestMsrAccessPolicy::from_host` validates an explicit caller-selected index sequence against a previously validated `HostMsrIndexList`. It is pure Rust: no KVM descriptor, raw UAPI structure, pointer, guest state, or ioctl is involved. Empty caller input is valid and returns an empty owned policy.

The general host list is the only capability source accepted by this constructor. Feature-MSR observations, immutable model candidates, composed CPU-model candidates, and vCPU readback values cannot confer membership. Every selected index must appear in the general supported set. An unsupported index returns `GuestMsrPolicyError::UnsupportedIndex` with its caller position; the constructor returns no policy object.

Caller duplicates are rejected rather than normalized. Host capability discovery normalizes duplicate kernel reports because those reports describe a set, but silently deduplicating caller authorization could hide a configuration mistake. `GuestMsrPolicyError::DuplicateIndex` therefore retains the index, its first position, and the later duplicate position. Validation is all-or-nothing: locally accumulated entries are dropped on any error, so no partial authorization state escapes.

Successful entries preserve caller order and are owned independently of both source inputs. Each entry currently carries `MsrAccessAuthority::ReadWrite`. This means only that the VMM policy permits a future read or write attempt for the index. It does not prove that every possible `u64` value is architecturally valid or that a future `KVM_SET_MSRS` call will process the entry; per-value KVM/MSR constraints remain a separate boundary. The policy stores no MSR values and performs no state mutation.

Policy membership is not a migration-safety claim. It records one caller-selected authorization constrained by one host's validated general MSR support snapshot. The policy is also deliberately separate from `VcpuMsrValues`: observing a vCPU value neither grants authority nor automatically adds an index to the policy.

### Guest MSR value-set validation

`GuestMsrValueSet::from_policy` accepts only an already validated `GuestMsrAccessPolicy` plus an explicit caller sequence of `(MsrIndex, u64)` state. It is pure Rust and has no descriptor, raw UAPI buffer, pointer, or ioctl side effect. An empty sequence is valid even when the policy authorizes additional MSRs.

The value set is deliberately a validated subset rather than a mandatory full image of the policy. Authorization breadth and one state fragment's breadth are separate. Every supplied index must match a policy entry with `MsrAccessAuthority::ReadWrite`; otherwise construction fails with `GuestMsrValueSetError::UnauthorizedIndex` and the caller position. The constructor cannot inherit authority from host feature observations, model candidates, or vCPU readback values.

Caller order is preserved exactly. Duplicate value indices are rejected rather than normalized, with both first and duplicate positions retained in `GuestMsrValueSetError::DuplicateIndex`. Validation is all-or-nothing: an unauthorized or duplicate entry prevents any `GuestMsrValueSet` from escaping, and locally accumulated values are dropped.

A successful set owns only `GuestMsrValue { MsrIndex, u64 }` records independently of the source policy and caller slice. It intentionally carries no `MsrFeatureStability` or host-model provenance because caller state is not a system feature-MSR observation. No policy/value-set check proves that a KVM write will accept the data: reserved-bit rules and other architectural constraints remain per-value kernel semantics. The value set grants no migration guarantee and causes no vCPU mutation until explicitly supplied to `Vcpu::set_msrs`.

### Full guest MSR snapshot

`GuestMsrSnapshot` is deliberately stronger than a general `GuestMsrValueSet`. The value-set type may represent an authorized strict subset, whereas a snapshot represents one complete ordered image of one complete `GuestMsrAccessPolicy`. Its constructor is crate-controlled so callers cannot directly certify arbitrary subset state as complete.

Snapshot construction first requires exact cardinality: the value count must equal the policy-entry count. It then validates every position so the value index exactly matches the policy index at the same offset. Missing, extra, or reordered values are rejected before a `GuestMsrSnapshot` exists. Empty policy plus empty values is valid.

A successful snapshot clones and owns both the policy and value set. It carries no raw UAPI buffer, pointer, descriptor borrow, or kernel authority; construction is pure Rust and issues no ioctl. The snapshot's stronger invariant is only complete policy coverage and order. It does not prove migration compatibility, cross-host validity, or future write success.

`Vcpu::capture_msr_snapshot` is the crate's current public way to obtain a snapshot from live vCPU state. It first delegates to `Vcpu::capture_msrs`, which itself uses the bounded all-or-nothing `Vcpu::msrs` readback path, then passes the complete capture through the crate-controlled snapshot constructor. No new raw ioctl or decoder is added. If lower-layer readback or full-policy validation fails, no snapshot is published.

`GuestMsrSnapshot::compare` is pure Rust over two already-valid full snapshots. It first compares their complete owned access policies. If the policies differ, `policy_matches` is false and value-level findings stay empty rather than interpreting differently shaped authorization state positionally. If the policies match, the snapshot invariant guarantees equal coverage and positional index identity, so only `u64` data values are compared. Each `GuestMsrSnapshotValueMismatch` retains the position, MSR index, reference value, and observed value.

`GuestMsrSnapshotComparison` clones and owns both snapshots; it contains no descriptor, KVM buffer, pointer, or authority to mutate guest state. `is_exact_match` means only that the two snapshot policies and values are equal under this project contract. It is not evidence of migration safety or cross-host compatibility and does not prove that either snapshot can be restored successfully.

### vCPU MSR writes

`Vcpu::set_msrs` accepts only an already validated `GuestMsrValueSet`; there is no public write overload that accepts arbitrary `(MsrIndex, u64)` state directly. This keeps caller authorization and value-state validation in front of the kernel mutation boundary. The method does not infer write state from host feature observations, model candidates, or `VcpuMsrValues`.

An empty set returns success before any ioctl. Non-empty values are copied in exact value-set order into a fresh fixed `KvmMsrs<1024>` object. Construction starts from all-zero header padding, entry reserved fields, and data; only the active entry indices and data are overwritten. The vCPU request builder rejects a count over 1024, while `sys::set_msrs` independently validates `nmsrs` against the actual const-generic buffer capacity immediately before its unsafe `KVM_SET_MSRS` call.

The returned processed-entry count is not treated as an atomic status. Exact completion is success. If KVM reports a short count, the successful prefix may already have modified vCPU architectural state. The method therefore returns `HostEnvironmentError::VcpuMsrPartialWrite` with vCPU id, requested count, processed count, and first unwritten index; it does not retry, roll back, or claim that no mutation occurred. A count greater than requested is rejected as `VcpuMsrInvalidWriteCompletion` rather than indexed into caller data.

A policy-authorized index still does not make every possible value writable. Kernel/MSR rules can reject a particular data value, and that rejection can appear as a zero or short processed count. The current write boundary performs one bounded attempt only. It does not automatically read back the result, sequence general registers/CPUID/device state, perform cross-vCPU restore orchestration, or make a migration-safety claim.

`Vcpu::restore_msr_snapshot` is the snapshot-bound restore entry point. It accepts one already-certified `GuestMsrSnapshot` and delegates exactly once to the existing `Vcpu::set_msrs(snapshot.values())` path. It does not rebuild, reorder, revalidate, or reinterpret the snapshot's policy/value coverage, and it introduces no new raw ioctl.

Restore inherits the direct write path's non-transactional completion semantics. A short `KVM_SET_MSRS` propagates `VcpuMsrPartialWrite` unchanged, including the fact that the processed prefix may already have mutated the target vCPU. The restore entry point does not retry or roll back.

`Vcpu::restore_and_verify_msr_snapshot` sequences one successful snapshot-bound restore with one recapture through the snapshot's own policy, then returns the existing owned `GuestMsrSnapshotComparison`. Write failure prevents readback; recapture failure propagates after the completed write without retry or rollback; a mismatch is reported rather than repaired automatically.

`Vcpu::verify_msr_snapshot` is a separate read-only boundary. It performs exactly one fresh full snapshot capture through the reference snapshot's own `GuestMsrAccessPolicy` and returns the existing pure comparison. It does not invoke `KVM_SET_MSRS`, restore, retry, repair, or rollback; a capture failure propagates unchanged and a mismatch remains comparison data.

### vCPU MSR readback and policy-bound capture

`Vcpu::msrs` accepts only an explicit caller-supplied `MsrIndex` slice and reads those entries from that specific vCPU descriptor. It does not consult or inherit `HostMsrFeatureValues`, `HostMsrModelCandidate`, or `CpuModelCandidate`; those are capability/model observations with different semantics. The KVM-aware regression chooses supported general indices as caller input, but the public primitive itself does not automatically derive a request set from any backend snapshot.

An empty request returns an owned empty `VcpuMsrValues` before `KVM_GET_MSRS` is issued. Non-empty requests use a fixed `KvmMsrs<1024>` object. The readback layer rejects more than 1024 caller entries with `InvalidInput` before reaching the raw ioctl, and `sys::get_msrs` independently validates the encoded `nmsrs` against the actual const-generic buffer capacity immediately before the unsafe call. Request construction leaves header padding, entry reserved fields, and initial data zeroed while copying caller indices in exact order; repeated indices are preserved rather than normalized.

The successful ioctl return is an untrusted processed-entry count. The decoder requires exact equality with the caller's requested count. A partial completion is rejected and identifies the first unread requested index; a count greater than requested is rejected as invalid response metadata. The supplied entry slice must contain the complete requested prefix, and every returned entry index must exactly equal the caller's index at the same position. Any mismatch rejects the whole response before a `VcpuMsrValues` result is created, so no successful prefix is published as a complete snapshot.

Only after all checks pass are the KVM entry data copied into owned `VcpuMsrValue` records. These records contain only the typed `MsrIndex` and architectural `u64` value. They intentionally do not carry `MsrFeatureStability`, because the stability metadata assigned to system feature-MSR observations is not a property of arbitrary guest vCPU architectural state. `VcpuMsrValues` owns its vector and carries no pointer or borrow into the request buffer or descriptor.

`Vcpu::capture_msrs` adds the policy boundary without adding another raw KVM operation. It extracts exactly the access-policy indices in policy order and delegates to `Vcpu::msrs`. Empty policy input returns an empty `GuestMsrValueSet` before the generic readback call and therefore issues no `KVM_GET_MSRS`.

Capture independently requires the readback to cover every policy entry and to retain positional index identity before converting it into a `GuestMsrValueSet`. This is intentionally stricter than the value-set type's general subset semantics: a partial prefix, changed index, or reordered internal result cannot escape as a successful policy-bound capture. `Vcpu::capture_msr_snapshot` then applies the full-snapshot coverage/order invariant to that complete value set and owns the policy/value pairing.

Readback, capture, full-snapshot certification, pure snapshot comparison, read-only snapshot-bound verification, direct write, snapshot-bound restore, and restore-and-verify remain separate state boundaries. None automatically adds sampled state to `CpuModelCandidate`/`CpuModelComparison`, automatically retries or repairs a restore, or claims stability across time or hosts. The current VMM is single-vCPU and has no concurrent scheduler; these state operations are invoked synchronously against the owned vCPU rather than racing an independently running vCPU thread.

### VM and memory setup

Before any vCPU exists, the VM backend configures KVM's x86 identity-map page and TSS pages in the reserved range `0xfeff_c000..0xff00_0000`. The required KVM capabilities are checked before VM creation, and guest RAM registration rejects overlap with this range.

The vCPU run structure is mapped using the exact positive size returned by `KVM_GET_VCPU_MMAP_SIZE`. The mapping must be at least large enough for every currently formed tested x86 prefix: the existing port-I/O view, the 48-byte fail-entry view, the capability-gated internal-error view (40-byte base without optional support or fixed 168-byte full view with support), and the 168-byte system-event view. Construction rejects a smaller mapping before any typed shared-memory cast can be formed; because the current system-event view already requires 168 bytes, enabling optional internal-error data does not enlarge the common mapping-size floor beyond that existing maximum.

For `KVM_EXIT_IO`, `data_offset` is treated only as an offset into the owned `kvm_run` mapping, never as a pointer. The vCPU layer checks conversion to `usize`, checked `size * count`, checked end-offset addition, and the final range against the mmap length before pointer arithmetic. OUT bytes are copied into an owned `Vec<u8>` before they cross into VM-exit policy or device code.

For `KVM_EXIT_IO_IN`, device policy returns owned response bytes rather than a pointer. Before copying those bytes into `kvm_run`, the vCPU layer re-checks that the current exit is port I/O, requires IN direction, recomputes the complete checked data range, and requires the response length to equal that range exactly. Only then does the unsafe copy target the validated region. OUT exits cannot be given an input response, and short or oversized responses are rejected.

For `KVM_EXIT_FAIL_ENTRY`, the tested fixed payload view begins at the `kvm_run` union offset and contains KVM's raw `hardware_entry_failure_reason` plus `cpu` field. Payload extraction first verifies that the current exit reason is fail-entry, then copies those scalar diagnostics into owned `VcpuFailEntry` state. No raw pointer or borrowed fail-entry data crosses into dispatch, and the dispatcher deliberately avoids `KVM_GET_REGS` or another vCPU ioctl that could replace the original entry-failure diagnostic with a secondary failure.

For `KVM_EXIT_INTERNAL_ERROR`, the tested base payload begins at `kvm_run` union offset 32 and contains the always-available raw `suberror: u32`. When the vCPU did not inherit positive `KVM_CAP_INTERNAL_ERROR_DATA` support, extraction forms only that base view, copies `suberror` into owned `VcpuInternalError`, and does not read `ndata` or `data[16]`; `data()` therefore reports `None`. When support is positive, extraction may form the fixed 168-byte full prefix containing `suberror`, `ndata`, and the 16-word data array. The kernel-reported count is converted and required to be `<= 16` before any Rust slice is formed; only the declared words are copied. `ndata == 0` produces available-but-empty data rather than capability absence. An invalid count returns structured `InvalidInternalErrorDataCount` diagnostics with vCPU id, `suberror`, reported count, capacity, and the execution loop later replaces its local reason trace with the complete ordered trace. No raw pointer or borrowed internal-error data crosses into dispatch, and dispatch deliberately avoids `KVM_GET_REGS` or another secondary vCPU ioctl that could obscure the original internal-error diagnostic.

For `KVM_EXIT_SYSTEM_EVENT`, the tested payload view begins at the same `kvm_run` union offset and contains a raw type, `ndata`, and fixed 16-word data capacity. Payload extraction first verifies that the current exit reason is system-event, then converts and rejects `ndata > 16` before forming the declared data slice. Only those declared words are copied into owned `VcpuSystemEvent` state. Known event-type values are typed, unknown raw values are retained, and neither the shared prefix pointer nor borrowed event data crosses into VM-exit policy.

KVM documents port-I/O operations as pending until userspace re-enters `KVM_RUN`. The dispatcher therefore services a request without taking a completed-operation register snapshot and returns `Continue`. For IN, the response buffer is populated before re-entry; KVM transfers it into guest architectural state when the following `KVM_RUN` completes the pending operation. The deterministic input fixture proves consumption by having guest code store AL into checked guest RAM and reading that RAM only after the later HLT exit.

`execution::run_vcpu_until_stopped` places a finite completed-exit budget around repeated `KVM_RUN` calls. The budget is checked before each run, and only a successfully completed VM exit consumes one unit. A zero budget therefore performs no guest run, while host-side `KVM_RUN` failures do not masquerade as completed guest exits. Every completed exit is appended exactly once to the ordered raw reason trace before dispatch.

When the configured budget is exhausted, the loop returns a structured `ExitBudgetExhausted` error with the vCPU id, configured limit, completed count, last completed raw exit reason when available, and the complete ordered completed-exit trace. Budget exhaustion is never converted into a terminal `VmExitReport`. If the final permitted exit was serviceable I/O, the userspace service may already be prepared, but without another permitted `KVM_RUN` the VMM does not claim that the pending KVM operation completed or snapshot registers as completed post-I/O state.

Unhandled raw-exit, fail-entry, internal-error (including malformed optional-data count), and system-event diagnostics likewise receive the complete ordered trace accumulated by the execution loop. A successfully returned fail-entry reason `9`, internal-error reason `17`, or system-event reason `24` is recorded once before payload decoding/dispatch, so the corresponding structured error retains that reason exactly once at the trace tail without implying resumable execution.

`VmExecutionResult` stores only owned Rust data: copied `PortIoExit` metadata/payloads, a terminal report, the completed-exit count, and the full ordered raw reason trace. `CpuidGuestResult` likewise stores only copied 32-bit observations and a terminal report. `VcpuMsrValues` stores only copied typed MSR indices and data. `GuestMsrAccessPolicy` stores only copied typed indices plus policy authority. `GuestMsrValueSet` stores only copied typed indices and caller-supplied data. `GuestMsrSnapshot` owns a complete copied policy plus the complete ordered value set certified against it. `GuestMsrSnapshotComparison` owns complete reference and observed snapshots plus its pure findings. General-register, special-register, and composite vCPU state snapshot/comparison values likewise own copied typed CPU state; their read-only verification methods borrow only the reference snapshot for one fresh capture and pure comparison, while restore methods retain no raw UAPI pointer or caller borrow after return. `Vcpu::set_msrs` copies value-set data into a temporary bounded KVM request object and retains no pointer or borrow after return; `Vcpu::restore_msr_snapshot` borrows the snapshot only for the duration of the delegated write attempt. `VcpuFailEntry` owns its copied hardware entry failure reason and CPU field, `VcpuInternalError` owns its copied `suberror` plus fixed optional-data storage/count when available, and `VcpuSystemEvent` owns its copied event type/data. Structured internal-error errors own copied optional data as `Option<Vec<u64>>` or malformed-count metadata; none borrows the shared mapping. None of these typed state values contains a pointer or borrow into `kvm_run`, guest RAM, a KVM request buffer, a vCPU descriptor, the policy/value caller slices, or the backend capability snapshots used to construct policy.

Guest RAM is a private anonymous mapping owned by `GuestMemory`. Region construction validates non-zero size, 4 KiB alignment, and guest-physical end arithmetic before `mmap` or KVM registration. After `KVM_SET_USER_MEMORY_REGION` succeeds, the `Vm` owns the mapping.

Before a `Vm` releases registered RAM, it explicitly removes KVM slot 0 with a zero-sized memory-region update. A separate vCPU fd may keep the kernel VM alive after the userspace VM handle begins destruction, so a failed unregister causes the mapping to be intentionally leaked rather than unmapped under a potentially live KVM slot.

Guest-memory read/write helpers validate guest address plus length against the registered region before any host pointer arithmetic. Flat-image loading uses those helpers; a guest physical address is never cast to a host pointer.

vCPU register ioctls use fixed-layout x86-64 UAPI structures. General registers are initialized from a fully zeroed structure plus explicit RIP/RFLAGS values. General-register capture owns all 18 fields; pure comparison and `verify_register_snapshot` use only typed copied values, and the verification path performs one fresh capture without calling the register setter or restore path. Snapshot-bound restore/restore-and-verify continue to use only typed copied values and the validated register setters/readback. Special-register capture owns semantic segment, descriptor-table, control-register, EFER, APIC-base, and interrupt-bitmap state without exposing KVM padding; it likewise supports pure comparison, read-only `verify_special_register_snapshot`, and bounded restore/restore-and-verify. `VcpuStateSnapshot` composes general-register, special-register, and policy-bound MSR snapshots, supports pure component-preserving comparison and read-only verification against a fresh capture, and sequences existing component restore operations with explicitly non-transactional semantics. These are vCPU CPU-state boundaries, not whole-VM or atomic/quiesced snapshots.

The minimal `PortIoBus` recognizes only debug port `0xe9`. The device accepts byte-wide, single-count accesses only. OUT requires exactly one copied payload byte; IN returns exactly one configured byte. Unknown ports, wide accesses, multi-count accesses, malformed OUT payloads, and malformed IN response lengths are explicit structured errors; no guest request is silently coerced.

## Not yet present

There is no guest virtual-address translation, external guest-image parser, MMIO, interrupt injection, configurable/migratable named CPU model, implemented `KVM_EXIT_SYSTEM_EVENT` lifecycle policy, fail-entry retry/CPU-placement/recovery policy, internal-error recovery/retry policy, virtqueue, disk backend, whole-VM/guest-memory/device snapshot orchestration, snapshot decoder, migration protocol, dynamic device registration, scheduler, or guest-controlled device descriptor parsing in this revision. The backend has bounded typed general MSR-index, feature-index, and stability-annotated feature-value capability snapshots; callers can derive provenance-bound immutable-only `HostMsrModelCandidate` values, compare them with `HostMsrModelComparison`, and compose that analysis with configured guest CPUID policy in `CpuModelCandidate`/`CpuModelComparison` without creating a migration guarantee. Guest MSR policy/value/capture/snapshot comparison, read-only snapshot-bound verification, bounded restore, and restore-and-verify are implemented. General-register, special-register, and composite vCPU state snapshots support owned comparison, read-only snapshot-bound verification, and bounded restore/restore-and-verify as documented above, but they do not include guest RAM or device state and do not claim atomic point-in-time capture, rollback, checkpoint, or migration semantics. `KVM_EXIT_FAIL_ENTRY` has typed owned fixed-payload diagnostics but no retry, placement, architecture-specific failure-bit interpretation, or recovery behavior. `KVM_EXIT_INTERNAL_ERROR` has typed owned `suberror` diagnostics on every exit and capability-gated optional `ndata/data[16]` copying on positively reporting hosts, including structured malformed-count rejection; it still does not translate `suberror` or data words into emulation recovery, retry, replacement execution, or lifecycle behavior. `KVM_EXIT_SYSTEM_EVENT` has typed owned payload extraction and structured unsupported diagnostics, but decoded events are not translated into reset/reboot/crash/shutdown/wakeup/suspend/SEV-termination/TDX-fatal VM lifecycle actions. Unsupported raw exits and unsupported port requests continue to be rejected with structured diagnostics rather than serviced heuristically.
